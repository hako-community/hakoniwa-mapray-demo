# S社向け Mapray広域運航管理デモ・実測検証計画

作成日: 2026-08-11
対象ワークスペース: `hakoniwa-mapray-demo`
対象SDK: Mapray JS `0.9.6`
計画対象: 実測安定性、5km級広域表示、運航判断価値の比較、およびGitHub公開準備前の成果整理
最終更新: 2026-08-11（Phase C Stage 1の目視合格と箱庭コアkinematic 30機liveを反映）

## 1. 結論

現在のR8判定は、次の二段階に分けて扱う。

- **技術PoC継続: Go**
- **Maprayを必須依存として正式採用: S社との運用・契約相談まで保留**

追加検証1〜3は別々のデモにせず、次の一続きのストーリーとして実装する。

> 5km級の渋谷広域を30機（性能未達時は20機）が巡回し、1機が計画経路を逸脱する。運航者がMapray上の警告から対象機を選択すると、Maprayは都市内の位置関係を示し、Three.jsは選択機の姿勢・局所地形・衝突建物へ切り替わる。最後に故障・衝突地点を両画面で同期して確認する。

この同一シナリオを用いて、以下を証明する。

1. 10機を回帰基準とし、20機・30機ではWebブラウザ単独構成と箱庭コア併用構成を10分以上動かし、OOMせず安定すること、および箱庭コアへの処理分離でブラウザ負荷が下がるかを実測する。
2. 600m局所表示だけでは得られない、5km級の地理的状況をMaprayで把握できる。
3. Leaflet＋Three.jsと比較して、異常機の発見・場所の理解・局所解析への移行が速く正確になるかを計測できる。

Maprayの役割は「物理演算」や「機体の精密描画」ではなく、**広域の地理的状況を運航判断へ変えるマクロビュー**とする。シミュレーション時刻と物理状態の正は箱庭コアおよびhakoSim／MuJoCo、機体詳細はThree.jsとする。

## 2. 現状認識と修正すべき評価上の問題

### 2.1 すでに確認できたこと

- `data/Mapray_test.mp4`で、Mapray DEM、Building Dataset 3件、10機、軌跡、Three.js局所表示が動作することを確認済み。
- OOM原因となった軌跡の高頻度・無制限更新を修正し、Mapray軌跡は1秒間隔・最大120点へ制限済み。
- Mapray API Keyが利用できない場合もLeaflet＋Three.jsへフォールバックできる。
- `FlightStateStore`により、パネル、Mapray、Leaflet、Three.js間の選択同期基盤がある。

### 2.2 現在のR7/R8レポートをそのまま根拠にしてはいけない理由

現行の`test_phase_r7_fleet_benchmark.ps1`は、ブラウザを計測せず、FPSとメモリを次の計算式で生成している。

```powershell
$estimatedMaprayFps = 60.0 - ($count * 0.8)
$estimatedThreejsFps = 60.0 - ($count * 0.3)
$memoryUsageMb = 85.0 + ($count * 2.4)
```

したがって、既存レポートの「20機、Mapray 44 FPS、Three.js 54 FPS、133 MB」は**実測値ではない**。新しい検証では、推定値を実測値として扱わず、既存R7レポートは`estimated`または`superseded`と明記する。

### 2.3 現行fixtureの制限

- R7 fixtureは10機固定で、実際の20機ブラウザ試験になっていない。
- 現在のPLATEAU/MuJoCo局所資産は原点周辺600m四方である。
- 現在のBuilding Dataset 3件も、600m局所用に抽出したCityGMLをテクスチャ数制限に合わせて分割したものである。
- 現在の運航GeoJSONは描画用FeatureCollectionだが、`flight_rules.mjs`は`geofences`と`plannedRoutes`へ正規化済みの形を期待している。表示される区域とルール判定が同じ入力を使うよう是正が必要である。
- 現行のデモ衝突は一部が合成イベントであり、実MuJoCo衝突と混同しない表示が必要である。

## 3. デモで伝える価値

### 3.1 S社向けメッセージ

デモの主メッセージを次に固定する。

> 箱庭コアとhakoSim／MuJoCoの物理シミュレーション結果をMaprayの実世界3D地図へ重ねることで、都市全体の多数機監視から、異常機の発見、現場位置の把握、機体の局所解析までを一つの画面でつなげられた。

### 3.2 各コンポーネントの役割

| コンポーネント | デモでの役割 | 正とする情報 |
|---|---|---|
| Mapray | 5km級の都市・地形、全機、経路、軌跡、ジオフェンス、事故地点 | 地理的状況と運航監視 |
| Three.js | 選択した1機の姿勢、ローター、局所地形、衝突建物 | 機体の視覚的詳細 |
| 箱庭コア＋hakoSim／`hako_drone_service`＋MuJoCo | マスター時刻、運動、故障、建物・地面との接触 | シミュレーション時刻と物理状態 |
| FlightStateStore | 全表示の機体・インシデント選択同期 | UI状態 |
| Leaflet | Mapray利用不能時の2Dフォールバック、および比較対照 | 2D地理表示 |

#### `hakoniwa-mujoco-runtime`との関係

この表の物理実行層は、`hakoniwa-mujoco-runtime`リポジトリ単体を意味しない。現在のWindowsデモで実際に起動する実行体は、インストール済みhakoSimの`hako_drone_service.exe`であり、同梱された`mujoco.dll`を使用する。

`hakoniwa-mujoco-runtime`は、MuJoCoの`WorldImpl`／`RigidBodyImpl`／アクチュエータ、箱庭アセットmanifest、PDU endpoint、conductor、asset lifecycleを提供する再利用可能な下位ライブラリである。単体で完成した30機シミュレーターとして起動するものではなく、最終的なPLANTまたはDrone serviceが、このライブラリ、`hakoniwa-core`、`hakoniwa_pdu_endpoint`、`libmujoco`等をリンクして実行する。

| 用語 | 本計画で指すもの |
|---|---|
| 箱庭コア | マスター時刻、アセット同期、開始・停止を管理する実行基盤 |
| hakoSim／`hako_drone_service` | 現在のWindowsデモで使用するドローン物理の実行体 |
| MuJoCo | hakoSim／PLANTが利用する物理エンジン |
| `hakoniwa-mujoco-runtime` | 新しいMuJoCo PLANTを構築するときに利用できるバックエンド＋箱庭アセット基盤ライブラリ |

20機・30機比較の第一候補は、現在動作確認済みのhakoSim／`hako_drone_service`を箱庭コアと組み合わせる構成とする。必要な複数機構成を実現できない場合に、`hakoniwa-mujoco-runtime`を利用した専用PLANTの実装を別タスクとして検討する。

### 3.3 Three.jsとは何か

Three.jsは、WebブラウザのWebGLを扱いやすくする汎用JavaScript 3Dライブラリである。scene、camera、light、mesh、material、animation、GLTF等の3Dモデル読込を組み合わせ、ブラウザ内に任意の3D空間を構築できる。

本デモでは、選択した1機の3Dモデル、姿勢、ローター回転、カメラ追従、MuJoCoと座標を合わせた600m局所地形、MJCF建物、衝突点・接触法線を表示する。Three.js自体はGISではなく、標準状態では緯度経度、世界DEM、地図タイル、都市データのLOD、広域地理検索を提供しない。その代わり、機体形状や物理空間を自由かつ精密に描けるため、**選択機を詳しく見るミクロビュー**に適している。

### 3.4 Leafletとは何か

Leafletは、Webブラウザで対話的な2D地図を構築する軽量JavaScriptライブラリである。地図タイル、marker、polyline、polygon、popup、GeoJSON、pan／zoom等を少ない実装量で扱える。

本デモでは、OpenStreetMap等の2D地図上への全機位置、経路、軌跡、区域、事故地点の表示、機体選択とThree.jsの同期、Maprayを利用できない場合のフォールバック、およびMapray 3D GISとのA/B比較を担当する。軽量で平面的な位置・経路確認には十分だが、地形の起伏、建物の高さ、飛行高度と都市空間の立体関係を標準機能だけで表現することは難しい。

### 3.5 Mapray、Three.js、Leafletの使い分け

| 確認したい内容 | 適した表示 | 理由 |
|---|---|---|
| 5km全体で30機の位置と異常を探す | Mapray | 地形・都市・高度を含む広域3D GISとして俯瞰できる |
| 選択機の姿勢、ローター、接触面を見る | Three.js | 任意の3Dモデルと物理座標を近距離で精密に描ける |
| API障害時も位置・経路を確認する | Leaflet | 軽量な2D地図として独立して動作できる |
| Maprayの運航判断価値を比較する | Leaflet＋Three.js | 2D広域＋3D局所という現実的な対照条件になる |

3つは競合する代替品ではなく、Maprayをマクロ3D、Three.jsをミクロ3D、Leafletを軽量2D／フォールバックとして組み合わせる。

### 3.6 Webブラウザと箱庭コアの責任分担

Webブラウザ単独で多数機の運動、故障、衝突、シナリオ時刻まで計算すると、描画負荷とシミュレーション負荷が競合し、タブ停止、時刻ずれ、再現性低下を招く。正式構成は箱庭コアを中心に置く。

```text
箱庭コア（マスター時刻・実行ライフサイクル）
  └─ hakoSim / hako_drone_service + MuJoCo（運動・制御・故障・衝突）
       └─ shared-memory PDU（機体状態・イベントの正本）
            └─ WebSocket Bridge（Web向け配信）
                 └─ FlightStateStore
                      ├─ Mapray（広域3D運航監視）
                      ├─ Leaflet（軽量2D／フォールバック）
                      └─ Three.js（選択機の局所3D解析）
```

| 層 | 担当するもの | 担当しないもの |
|---|---|---|
| 箱庭コア | マスター時刻、開始・停止、複数機同期、シナリオ進行 | 地図描画、ブラウザUI |
| hakoSim／`hako_drone_service`＋MuJoCo | 運動、姿勢、制御、故障、衝突、接触情報 | 広域地理表示 |
| PDU／WebSocket Bridge | 状態・イベントの運搬、機体IDの維持 | 物理計算、表示上の補間以外の状態生成 |
| Webブラウザ | 描画、選択、警告提示、カメラ同期、計測 | 物理・衝突・シミュレーション時刻の正本 |

ブラウザ側fixtureは表示負荷試験として残すが、箱庭コアを含むE2Eの証拠にはしない。S社向け本番デモは原則`LIVE HAKONIWA`とし、通信切断に備えた代替だけを`REPLAY`として用意する。PDU受信頻度、画面描画頻度、軌跡サンプリング頻度を分離し、古い状態を無制限にキューへ蓄積しない。

### 3.7 デモで主張しないこと

- MaprayがMuJoCoの代わりに衝突判定するとは主張しない。
- 合成30機を「30機の箱庭コアE2E」と表現しない。
- 600m分のB3Dしかない状態で「5km全域の高精細Building Datasetを配信済み」と表現しない。
- 計算式で生成したFPS・メモリを実測値として提示しない。
- Mapray Cloudの費用、商用条件、SDK移行可否を解決済みと表現しない。

## 4. 統合デモシナリオ

### 4.1 シナリオ名

**Shibuya 5km Fleet Operations and Incident Drill**
日本語表示名: **渋谷5km・複数機巡回／異常対応デモ**

### 4.2 シナリオ構成

1. **広域巡回開始**
   - 本番目標30機を5km級の範囲へ配置する。性能基準を満たさない場合は20機へフォールバックする。
   - 複数の計画経路、運航区域、進入禁止区域、離着陸拠点を表示する。
   - Maprayを広域監視72%、Three.jsを選択機詳細28%で表示する。
2. **正常状態の俯瞰**
   - 全機の現在位置、機体ID、状態、直近120秒の軌跡を表示する。
   - 選択機だけを強調し、ラベル密集時は非選択機ラベルを縮小またはクラスタ化する。
3. **経路逸脱の発生**
   - 決定論的な時刻に1機へ風またはローター異常を注入する。
   - 計画経路からの逸脱、ジオフェンス違反、高度違反の最低1種類を発生させる。
   - Mapray上で異常機、逸脱区間、警告地点を視覚的に区別する。
4. **運航者による異常機選択**
   - 警告一覧またはMapray上の機体を選択する。
   - Maprayカメラは異常地点へ移動し、Three.jsは同じ機体へ追従する。
   - 左パネルに機体ID、違反種別、発生時刻、距離・高度差を表示する。
5. **局所解析**
   - 対象機が600m局所物理領域へ入った段階で、Three.jsに局所地形・MJCF建物・機体姿勢を表示する。
   - 実MuJoCo衝突または「合成／リプレイ」と明示した衝突イベントを発生させる。
   - 衝突点と推定法線をMapray、Leaflet、Three.jsで同期する。
6. **広域へ復帰**
   - Maprayを再び5km表示へ戻し、異常対応中も残りの機体が運航中であることを示す。
   - デモ終了時に実測サマリーを画面とJSONへ出力する。

### 4.3 再現性

- URLまたは設定で`fleetSize=10|20|30`、`seed`、`durationSec`、`scenarioMode=fixture|replay|live`を指定できるようにする。
- S社向け本番デモは固定seedと固定タイムラインを使用する。
- すべての画面に`SYNTHETIC FLEET`、`REPLAY`、`LIVE HAKONIWA`のいずれかを表示する。
- 自動デモと手動操作を切り替えられるようにし、途中で機体を選択してもシナリオ進行を壊さない。

### 4.4 機数と比較構成の方針

| 機数 | 位置付け | 用途 |
|---:|---|---|
| 10機 | 回帰基準 | 既存機能とOOM修正を壊していないことの確認 |
| 20機 | 最低合格ライン | Webブラウザ単独と箱庭コア併用の正式比較、E2E Go／No-Go判定 |
| 30機 | S社向け本番目標 | 3経路×10機等へ分散し、広域の多数機運航管理を示す |

10機は回帰試験だけに使用する。20機・30機では、ブラウザ内で決定論的状態を生成する`browser-standalone`と、箱庭コアから状態を受信する`hakoniwa-core`を同条件で比較する。30機が性能・視認性基準を満たさない場合は20機を正式デモ構成とし、30機結果はstress testとして提示する。50機以上は将来の負荷試験候補とする。

`browser-standalone`はブラウザ単独性能、`hakoniwa-core`はPDUとBridgeを含むE2E性能として報告する。箱庭コア側が20機までの場合は20機を`LIVE HAKONIWA`、30機を`SYNTHETIC FLEET`のstress testとして明確に分ける。

## 5. 検証1: 10機回帰、および20機・30機の実測安定性比較

### 5.1 実装方針

`hakoniwa-geo-viewer`へブラウザ実測モジュールを追加する。最低限、次を記録する。

- `requestAnimationFrame`によるページ全体のフレーム時間
- FPS中央値、5パーセンタイルFPS、95/99パーセンタイルフレーム時間
- Long Task件数と合計時間
- `performance.memory`が利用可能なChromiumではJS Heap使用量・上限
- Mapray Drone Pin、軌跡、インシデント、運航レイヤのEntity数
- 軌跡点数、インシデント数、Store内機体数
- 初期化開始からMapray ready、B3D ready、Three.js readyまでの時刻
- uncaught error、unhandled rejection、WebGL context lostの有無
- ブラウザ、OS、GPU、画面解像度、Mapray SDK版、シナリオseed

MaprayとThree.js個別のFPSを公開APIで正確に分離できない場合は、架空の個別FPSを出さない。代わりに次の3モードを同じブラウザ・同じ条件で比較する。

1. `mapray-full`: Mapray＋Three.js
2. `mapray-base`: Mapray標準DEM/地図＋Three.js（Building Datasetなし）
3. `leaflet-fallback`: Leaflet＋Three.js

結果名は`pageFps`、`jsHeapMb`、`entityCounts`のように測定対象が分かる名称にする。

### 5.2 測定プロトコル

- 対象ブラウザ: S社向けデモで使用予定のChromeまたはEdge。バージョンをレポートへ記録する。
- URLはMapray Allowed Domainに合わせ、必ず`http://localhost:18080`を使用する。
- 1条件につきウォームアップ2分＋測定10分とする。
- 各条件を最低3回実行し、中央値を採用する。
- 10機は既存機能の回帰試験として測るが、アーキテクチャ負荷比較の主対象にはしない。
- 20機・30機を`browser-standalone`と`hakoniwa-core`の同条件で測る。20機は最低合格判定、30機は本番採用判定に使う。
- `scenarioMode=fixture`を`browser-standalone`、`scenarioMode=live`を`hakoniwa-core`として対応付け、レポートには両方の名称を記録する。
- 箱庭コア試験では箱庭コアの実行時刻とブラウザ受信時刻を記録し、遅延、更新欠落、機体ID不一致を測る。
- 測定中は固定カメラだけでなく、広域→異常地点→広域のカメラ移動を同じ時刻に実行する。
- バックグラウンドタブ化、ウィンドウ最小化、DevToolsの常時表示を避ける。
- GPUドライバ、電源モード、画面解像度を固定する。

### 5.3 合格基準

| 項目 | 合格基準 |
|---|---|
| 安定性 | 10分間、OOM、クラッシュ、WebGL context lost、未処理例外なし |
| FPS | 10機・20機・30機ともページFPS中央値30以上、5パーセンタイル20以上。30機だけ未達の場合は20機へフォールバック |
| メモリ | 軌跡上限到達後のJS Heap増加傾向が2 MB/分以下、測定後半5分で20%以上の単調増加なし |
| Entity | 機体、軌跡、インシデントのEntity数が設定上限を超えず、時間に比例して増加しない |
| 操作 | 機体選択から両カメラ同期まで500 ms以内 |
| 再現性 | 同一条件3回のページFPS中央値の差が20%以内 |
| E2E | 箱庭コアlive 20機で表示遅延が継続的に増加せず、機体ID欠落・重複なし。30機も同基準を本番目標とする |

機種依存が大きい絶対メモリ値だけで合否を決めず、**上限到達後にメモリが収束すること**を重視する。

### 5.5 Webブラウザ単独と箱庭コア併用の負荷比較

20機・30機では、描画条件を揃えたまま実行主体だけを変えるA/B試験を行う。

| 比較構成 | 状態生成・時刻進行 | ブラウザの担当 | 評価目的 |
|---|---|---|---|
| `browser-standalone` | ブラウザ内の決定論的scenario player | 状態生成、ルール評価、表示、UI | ブラウザ単独でどこまで安定動作できるか |
| `hakoniwa-core` | 箱庭コア、hakoSim／`hako_drone_service`、MuJoCo | WebSocket受信、表示用変換、表示、UI | 状態生成を外へ出すことでブラウザ負荷と応答性が改善するか |

#### 比較条件

- 機数は20機・30機とし、10機はこの比較には使わない。
- 経路、異常発生時刻、カメラ遷移、軌跡上限、表示レイヤ、画面解像度を揃える。
- 状態更新頻度を揃える。箱庭コアの物理ステップが高頻度でも、Bridgeからブラウザへ配信する頻度は比較用の一定値へ整形する。
- 可能な範囲で同じ位置・姿勢系列を使用し、物理モデル差と実行主体の効果を混同しない。
- `mapray-full`、`mapray-base`、`leaflet-fallback`の各表示モードで比較する。
- ウォームアップ2分、測定10分、各条件3回を共通化する。

#### ブラウザ側の比較指標

- ページFPS、95／99パーセンタイルフレーム時間、Long Task
- JS Heap、GC変動、ブラウザプロセスCPU、Working Set
- 受信状態キュー長、破棄・上書き件数、最新状態との遅延
- Entity数、軌跡点数、再生成回数
- 機体選択、警告選択、カメラ同期の応答時間

ブラウザプロセスCPUとWorking Setは、Windows側の計測スクリプトまたはChrome DevTools Protocolで収集する。

#### システム全体の比較指標

- ブラウザ、箱庭コア、MuJoCo、WebSocket Bridgeを合計したCPU使用率とWorking Set
- 箱庭コア時刻からブラウザ表示までのE2E遅延
- PDU更新数、WebSocket送信数・バイト数、更新欠落数
- シミュレーション実時間比と時刻ずれ

箱庭コア併用では、ブラウザCPUやLong Taskが減っても、システム全体のCPU・メモリは増える可能性がある。その場合も「総処理量が減った」とは表現せず、**ブラウザの応答性と安定性を確保するために処理を適切なプロセスへ分離できた**と評価する。

#### 評価目標

- 20機・30機で`hakoniwa-core`のページFPSと操作応答が`browser-standalone`と同等以上。
- ブラウザプロセスCPU中央値またはLong Task合計時間のいずれかが20%以上改善。
- JS Heapと状態キューが時間に比例して増加しない。
- E2E遅延が測定後半に向けて増加せず、最新状態への追従を維持。
- 機体ID、異常時刻、位置・姿勢の欠落や取り違えなし。

改善が小さい場合は、負荷の主因が状態生成ではなくMapray／Three.js描画である可能性を示す。その場合は箱庭コアの価値を負荷削減だけで判断せず、物理の正本、時刻同期、再現性、複数プロセス連携も分けて報告する。

### 11.3 統合workspaceのGit管理方針

ワークスペース直下の`scripts/`と`runtime/`は、3つの製品リポジトリを横断して
Windows上のシミュレーション、WebSocket Bridge、Viewer、CityGML変換を起動する
統合層である。現状のワークスペース直下はGitリポジトリではないため、再現性に必要な
内容を統合用の第4リポジトリ`hakoniwa-mapray-demo`で管理する。リポジトリ名は確定とし、
GitHubへ作成・公開する時期は別途調整する。公開時期が決まるまでは、ワークスペース直下の
統合資産をローカルで維持する。

統合リポジトリでGit管理するもの:

- `scripts/windows/`のPowerShell・Pythonソースとテスト
- `runtime/windows/README.md`
- `runtime/windows/config/.env.example`
- `runtime/windows/config/windows.paths.example.json`
- `runtime/windows/scenarios/`の入力定義、必要最小限のシナリオ資産
- 3つの公開リポジトリを取得するsubmodule定義または固定revision manifest
- クリーン環境でのセットアップ、doctor、起動、停止、回帰試験の手順

Git管理しないもの:

- `runtime/windows/config/.env`、`*.local.json`、API Key、Token
- `runtime/windows/.venv-city/`
- `runtime/windows/generated/`、`logs/`、`mmap/`、`state/`
- 実行時に生成される`drone_log*/`、PID、キャッシュ、`__pycache__/`
- 再配布条件が確認できていない原本データ、インストール済み実行ファイル・DLL

`runtime/`という名前は「すべて非管理」を意味しない。再現可能な入力とテンプレートは
管理し、マシン固有状態と再生成可能な出力だけを`.gitignore`で除外する。既存3リポジトリへ
横断起動スクリプトを分散するとrevision整合と利用手順が分かれやすいため、統合リポジトリを
公開単位とする。リモートリポジトリの作成・pushは、公開時期と公開範囲について合意した後に行う。

## 12. GitHub公開準備ゲート

本計画完了後、GitHub公開準備では最低限、次を確認する。

1. `MAPRAY_API_KEY`、Access Token、Cookie、ローカル環境情報のsecret scan。
2. `.env`、実測時のブラウザプロファイル、個人情報を除外。
3. Mapray、PLATEAU、国土地理院、OpenStreetMap等のライセンス・attribution確認。
4. Mapray Dataset IDを公開してよいかS社へ確認。
5. Mapray JS 0.9.6 CDN利用条件と、公開デモのAllowed Domain設定を確認。
6. 635MBのCityGML ZIP、生成物、87MB動画をGit履歴へ直接追加しない。
7. 大容量成果物はGitHub Release、外部ストレージ、または再生成手順へ分離。
8. Windows絶対パスを設定・スクリプトから排除し、リポジトリ相対パスへ変更。
9. 初回利用者向けREADME、`.env.example`、起動コマンド、フォールバック手順を用意。
10. 公開前にクリーン環境で自動テストとsmoke testを実行。
11. 統合リポジトリでは、`runtime/`の管理対象と除外対象を`.gitignore`で明示する。
12. submoduleまたはrevision manifestが、検証済みの3リポジトリrevisionを指すことを確認する。

## 13. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 30機で再びメモリ増加 | OOM、デモ停止 | 10／20／30機の段階測定、軌跡・インシデント・Entity上限、10分実測、長時間回帰 |
| ブラウザが箱庭コア処理に追い付かない | 表示遅延が蓄積、古い状態を表示 | 最新状態優先、受信と描画の分離、キュー上限、E2E遅延監視 |
| 箱庭コア併用で総CPU使用量が増える | 「負荷削減」の説明が不正確になる | ブラウザ負荷とシステム全体負荷を分離し、応答性改善と総処理量を別評価 |
| standaloneとcore-backedで状態更新頻度が異なる | 公平な比較にならない | Bridge配信頻度、経路、seed、表示条件を固定し、差分をレポートへ記録 |
| MaprayとThree.jsの描画負荷を誤って個別FPSと表記 | 評価の信頼性低下 | 分離できない場合はページFPSとして報告、モード比較で寄与を測る |
| 5km B3Dが未整備 | MaprayのLOD価値が弱い | Stage 1とStage 2を明確化し、未整備範囲を表示 |
| ラベル・軌跡が30機で密集 | 状況把握が困難 | 選択強調、状態色、ズーム別ラベル、必要ならクラスタリング |
| GeoJSON表示とルール判定の不一致 | 誤警告、デモ破綻 | 単一正規化モデル、単体テスト、正解fixture |
| Cloud/API Key障害 | デモ不能 | Leafletフォールバック、事前疎通、キャッシュ依存を避ける |
| 合成データを実E2Eと誤認 | 対外説明上の問題 | 常時モード表示、資料・レポートへデータ由来を記載 |
| Mapray 0.9.6固有実装 | 長期保守負担 | adapter内へ隔離、移行はS社相談後の別計画 |
| 参加者が少なくA/B結果が不安定 | 価値判断が弱い | 最低3名・目標5名、順序交互、結果を参考値と明記 |

## 14. 最終判定基準

### Mapray継続Go

次をすべて満たす場合、Maprayを任意の広域運航管理レイヤとして継続Goとする。

- 箱庭コアlive 20機・10分実測でOOMせず、FPS・E2E遅延・メモリ・Entity上限を満たす。
- live 30機でも同基準を満たす場合はS社向け本番を30機とし、未達の場合は20機を正式構成、30機をstress testとする。
- 5km級の全機・経路・区域・異常地点を一画面で把握できる。
- 広域から局所Three.jsへ機体IDを保ったまま移行できる。
- A/B評価で正答率または作業時間に定量的改善がある。
- Maprayなしでもシミュレーションと局所解析が成立する。

### 保留

- 技術基準は満たすが、A/B評価で明確な差が出ない。
- 5km B3Dが未整備で、標準地図／DEMだけの評価に留まる。
- S社とのCloud費用・Dataset運用・SDK方針が未決定である。

この場合もMapray adapterは任意機能として保持し、必須起動経路にはしない。

### No-Go

- 箱庭コアlive 20機・10分でメモリまたはE2E遅延が収束しない、もしくは操作可能なFPSを維持できない。
- Leaflet＋Three.jsと比較して運航判断の改善がなく、3D背景以上の価値を示せない。
- Mapray依存によりフォールバックを含む基本シミュレーションが不安定になる。

## 15. 推奨実施順序

実装順は次とする。

1. **Phase A**: 評価基盤と既存レポートの是正
2. **Phase B**: 10機回帰、および20機・30機のWebブラウザ単独／箱庭コア併用比較
3. **Phase C Stage 1**: 5kmシナリオと統合デモ
4. **Phase D**: Mapray／Leaflet運航判断比較
5. **Phase E**: S社向けデモ仕上げ
6. **S社相談**: Cloud、5km B3D、SDK、費用・公開条件
7. **Phase C Stage 2（許可後）**: 5km B3D Dataset拡張
8. **GitHub公開準備**: secret、ライセンス、大容量資産、README、クリーン環境検証

最初に実測基盤を作ることで、後続の5kmデモ改善を毎回同じ指標で評価できる。Cloud更新を後段へ分離することで、S社との相談前でも1〜3の主要部分を進められる。
